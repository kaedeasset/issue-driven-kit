# Issue を無人の Claude に進めさせる（issue-run）

GitHub Issue にラベル `claude-run` を付けておくと、`Scripts/issue-run.ps1` が1件ずつ新しい Claude Code（`claude -p`・auto mode）を起動し、**Issue の合格の条件を満たすまで**設計・実装・テストを回させる。時間帯は関係ない（2026-10-15 に `-Mode night/day` を廃止。動きが同じだったため）。自分が作業していない worktree を選んで起動し、終わったら確認する。worktree を変えれば、複数を同時に回せる。検討の経緯は `Docs/Reports/2026/10/14/03`。

## 考え方

- **設計の正はリポジトリの文書。** Issue は「どの文書のどこを、どの合格の条件まで」を指すだけ。設計そのものを Issue に書かない（CLAUDE.md 原則6）。
- **合格の条件と確認コマンドが必須。** ゴールと決まった判定が無いと回らない。どちらかが無い Issue は起動しない。公式も「決まった判定が一番強い」「一番の失敗は早すぎる勝利宣言」としている（`Docs/Reports/2026/10/14/04`）。
- **判定に使うファイルは変えさせない。** 確認コマンドに出てくるリポジトリのファイル（テストのスクリプト等）は、開始時の中身から変わっていたら合格にしない（公式の「テストを書き換えない」）。テストの側を直す Issue なら、確認コマンドは別の既存の入口から呼ぶ。
- **決定待ちで止まらない。** 書いていない決定は Claude が「git で戻せて範囲が小さいほう」を選び、選んだことと戻し方を報告に書く（CLAUDE.md 原則1）。
- **コミットまで。** push と Issue を閉じるのは、確認したユーザーがやる（push は main のセッションから）。
- **コミットの形はフックが検査する。** 無人の実行でも `commit-msg`・`pre-commit`（`Tools/commit-hooks/hooks/`）が効く。止まったら表示に従ってメッセージか中身を直す（プロンプトにコミットの書き方は書かない。フックの表示が正）。

## 止まらない仕組み

指示文に「止まるな」と書くだけでは保証にならない。止まる原因ごとに、仕組みの側で塞ぐ。

| 止まる原因 | 塞ぎ方（どこで） |
|---|---|
| Claude が区切りで返答を終える（`-p` はそこで終わる） | **Stop hook**（`.claude/issue-run/stop-hook.ps1`）。報告ファイルが「## 結果: 合格」・判定に使うファイルが開始時のまま、の2つがそろうまで返答を終えさせない（押し返しは合計30回。別に Claude Code 自身が「ツールを呼ばずに8回続けて」で打ち切る）。終わったら、スクリプトが Issue の確認コマンドを **1 回だけ**回し、落ちていれば出力を付けて同じ会話を `--resume` で再開する（最大 `-MaxRounds` 回）。hook と判定役のエージェントは確認コマンドを回さない（2026-10-15: 3 か所で回していて、重い確認が 3 倍かかった） |
| 確認の画面が出る | CLI の `--permission-prompts none`。確認は出ずに断られ、エラーが Claude に返るだけ（止まらない） |
| 質問する | `--disallowed-tools AskUserQuestion` と deny |
| 承認の要る操作（削除・プロセス停止・push・Issue への書き込み・リポジトリ直下の CLAUDE.md と `.claude/` の書き換え・`Docs/InSpecs/`〔人が書く入力の文書の置き場。2026-11-13 に足した〕の書き換え・履歴の書き換え） | 設定の **deny** で必ず断る（auto mode の判定まかせにしない。deny の `CLAUDE.md`・`.claude/**` は gitignore の規則で**どの深さにも**効く〔公式の説明。2026-10-16 の「直下だけに狭めた」は効いていなかった〕。製品の雛形 `Templates/NewWork/` の CLAUDE.md とスキルまで断っていて、#33・#34・#40・#15 がそこだけ書けずに終わったので、2026-10-17 に deny を `Edit(//{{REPO}}/CLAUDE.md)`・`Edit(//{{REPO}}/.claude/**)` の**絶対パス**に変え、直下だけに効かせた〔`{{REPO}}` はスクリプトが作業場所の POSIX 形 `d/Unreal Projects/kaedevn-rpg` に置き換える。gitignore の `!` の打ち消しと `./` の形は実測で外れなかった・`/path` は `--settings` のファイルの場所が基準なので使えない〕。実測: 雛形のスキルと CLAUDE.md は書けて、直下の CLAUDE.md・`.claude/`・`Server/kaede-rpg-server/CLAUDE.md` は断られる。雛形の `.claude/` は Claude Code の「守る場所」でもあるので、書き込みは auto mode の判定器に回る）。指示文にも代わりのやり方を書いてある。Issue へのコメントとラベルはスクリプトが行う |
| コマンドが10分で時間切れ | 設定の env `BASH_MAX_TIMEOUT_MS`（90分） |
| 実行中に Claude Code が更新されて版が変わる | 設定の env `DISABLE_AUTOUPDATER` |
| 認証切れ・利用上限 | 起動前の点検で止める・上限は待ってやり直す |
| 設定が読まれていない（`-p` は壊れた設定を黙って無視する） | 起動前の点検で、Stop hook が呼ばれたことと deny が効いたことを実際に確かめる。だめなら Issue に触る前に止まる |
| PC のスリープ | 動いている間だけスリープを止める（設定は変えない） |
| 起動した窓の中をクリックして選択モードになり、画面への出力で止まる（2026-10-14 に24分止まった） | 動いている間だけ、その窓の簡易編集モードを切る（終われば戻す。窓のプロパティは変えない） |

設定は `.claude/issue-run/settings.json`（`--settings` で渡す。対話のセッションには効かない。権限は狭めるだけで広げない）。

それでも残るもの: 1回の上限（`-RoundMinutes` 90分）×回数（`-MaxRounds` 4）で合格しなければ `claude-failed` にして次の Issue へ進む。auto mode の判定で、deny に無い操作が断られることはある（断られたツールは Issue ごとの記録に出る）。

**判定不能**: 作る側をどう直しても合格できない Issue（合格の条件どうし、または条件と守るファイルが両立しない）は、Claude が報告ファイルを判定不能の形（1 行目 `## 結果: 判定不能` と、中身のある節 `## 両立しない条件`。ぶつかる 2 つ・なぜ両立しないか・直し方の推し）にする。Stop hook は押し返さず（回数も数えない）、スクリプトは確認コマンドを回さず、次の回へ進まずに `NOT-PASS`・`claude-failed` にして人へ返す。コメントの「合格しなかった理由」は「報告が判定不能（合格の条件が両立しない）。人が Issue の条件か守るファイルを直す。」と節の中身。直して `claude-failed` を外すと再び対象になる。見分ける決まりは `Scripts/issue-run.ps1` の `Get-UndecidableReport` と `stop-hook.ps1` の 2 か所にあり、同じにしておく（2026-11-13 にキットの Node 版から取り込んだ。それまでは 30 回押し返して 4 回まで回していた）。

## ラベル

| ラベル | 付ける人 | 意味 |
|---|---|---|
| `claude-run` | ユーザー | やってよい。ひな形から作ると最初から付く |
| `claude-working` | スクリプト | 実行中（前回が落ちて残っていれば、次の起動で外す） |
| `claude-done` | スクリプト | 合格した。確認して閉じる |
| （前提待ち） | スクリプト | ラベルは付けない。本文の「## 前提」の Issue が済むまで始めず、Issue ごとの記録に WAITING と出る |
| `claude-failed` | スクリプト | 合格の条件か確認コマンドが無い・回数切れ・判定不能（合格の条件が両立しない）・異常終了。理由はコメント。直して外すと再び対象になる |

ラベルは最初の実行で自動で作られる。

## 準備（最初の1回）

1. PowerShell 7（`pwsh`）で動かす（スクリプトの頭に `#Requires -Version 7`。Windows PowerShell 5.1 では起動しない）。`gh auth status` が通ること。
2. 無人の `claude -p` は対話のログインと別に認証が切れることがある（2026-10-14 に `OAuth session expired` で実際に落ちた）。長期のトークンを作って環境変数に入れる:
   ```
   claude setup-token
   [Environment]::SetEnvironmentVariable('CLAUDE_CODE_OAUTH_TOKEN', '<表示されたトークン>', 'User')
   ```
   新しいターミナルを開いてから使う。
3. `.claude/issue-run/settings.json` があること（無ければスクリプトは止まる）。
4. 試し: `pwsh Scripts\issue-run.ps1 -DryRun` で、対象の Issue・合格の条件の行数・守るファイル・渡す指示文を見る。合格の条件（箇条書きと確認コマンド）に、設定の deny が書き換えを断るパス（`settings.json` の `Edit(//{{REPO}}/…)`・`Write(//{{REPO}}/…)`。いまは直下の `CLAUDE.md`・`.claude/**`・`Docs/InSpecs/**`・`Server/kaede-rpg-server/CLAUDE.md`）に当たる語があれば、Issue ごとに「deny のパス: <語>, …」の 1 行で知らせる（関数 `Get-DenyEditPaths`・`Get-DeniedMentions`）。知らせるだけで起動は止めない。直させる条件なら人が直す（`issue-goal-setting.md` 4.4）。

## 起動

```
pwsh Scripts\issue-run.ps1                    # ラベル claude-run の付いた Issue を全部、順に
pwsh Scripts\issue-run.ps1 -Issue 12          # 1件だけ
pwsh Scripts\issue-run.ps1 -WorkDir 'D:\Unreal Projects\kaedevn-adv'   # 作業場所を指定（選ぶ画面を出さない）
```

| 引数 | 既定 | 意味 |
|---|---|---|
| `-RoundMinutes` | 90 | 1回の起動の上限。超えたら打ち切って、同じ会話を再開する |
| `-MaxRounds` | 4 | 再開の回数の上限。超えたら `claude-failed` |
| `-MaxIssues` | 20 | 1回に回す件数の上限 |
| `-LimitWaitMinutes` / `-MaxLimitWaits` | 30 / 16 | 利用上限に当たったら待ってやり直す（最大8時間。回数に数えない） |
| `-Model` | `claude-opus-5-5`（Opus 5.5） | 無人の回に使うモデル。対話の既定（`~/.claude/settings.json` の `model`）には引きずられない。変えるなら `-Model sonnet` など（2026-10-16 ユーザー指示） |
| `-WorkDir` | （選ぶ） | 作業場所の worktree。指定すると選ぶ画面を出さない |

- **作業場所は起動するときに選ぶ。** 窓から起動すると worktree の一覧が出るので、番号で選ぶ（Enter なら起動したフォルダー。一覧の `*`）。入力が窓でない（ほかの仕組みから起動した）ときは、起動したフォルダー。スクリプトの置き場では決めない。自分が作業している worktree とは別のものを選ぶ（同じファイルを同時に触らないため。新しく作らず既存のものを使う）。
- **worktree ごとに 1 本ずつ、同時に動かせる。** 同じ worktree で二重に起動すると、後から起動したほうが止まる（一覧でも「実行中」と出て選べない）。同時に動かすときの決まり:
  - 同じ Issue を取り合ったら、両方とも譲って次へ進む（いま進めている番号は `Saved/IssueRun/run.issue`）
  - 起動時に「実行中」のラベルを外す掃除は、ほかの worktree で動いている Issue のラベルには触らない
  - 「## 前提」の Issue が `claude-done` でも、合格したコミット（コメントの頭の `HEAD`）がその worktree のブランチに無ければ始めない（閉じられていれば始める）
  - UE のビルドは同時 1 本のまま。片方がビルドやエディタを動かしていると、もう片方はその回ではビルドせず、ビルドの要る条件を「未判定」にして再開を待つ（下の行）。ビルドの要る Issue どうしを同時に流すと、回数を使い切りやすい
- **確かめは CLI で、UE の組み立ては最終段階だけ**（書き方は `issue-goal-setting.md` の 4.3）。無人の Claude にも、変えた所に関係する CLI のテストだけを回させ、UE の組み立て・エディタ・L4 は確認コマンドが使う Issue でだけ、最後に 1 回させる（指示文）。
- UE エディタ・ビルドが動いていると、その回ではビルドとエディタの起動を禁じて渡す（同時1本）。ビルドの要る条件は「未判定」のまま再開を待つ。

## 動いている間に見るもの

`claude -p` は終わるまで窓に何も出さない。進み具合は、逐次書かれる会話の記録 `~/.claude/projects/<プロジェクト>/<セッションID>.jsonl` の最新のものを見る（ツールの呼び出しが並ぶ）。セッション ID は `Saved/IssueRun/<日時>/` の各回の JSON にも出る。

## 終わった後に見るもの

読み方と、合格しなかったときの直し方は `Docs/Guides/Procedures/issue-goal-setting.md` の 8 章。ここは置き場だけ。

1. `Docs/IssueRuns/issue-NNNN.md`（NNNN は Issue の番号を 4 桁に。例 #101 は `issue-0101.md`）— Issue ごとの記録。回ごとに `## <回の日時> — <結果>` の節を下へ書き足す（古い回が上）。分・回数・コミット・断られたツール・理由・報告がここに出る。Issue の番号は変わらないので、同じ Issue の何回目でも同じファイル。Issue を 1 件も扱わずに止まった回（認証切れなど）は書かない（画面とログに出る）。2026-10-22 に `Docs/Reports/` の回ごとのまとめ 28 本から移した
2. 各 Issue のコメント — 頭の行に結果・**かかった分と開始〜終了の時刻**（分の単位。例 `6 分（2026-10-22 09:36〜09:42）`。始まりは「実行中」のラベルを付けた直後、終わりは合否が決まった時。起動前の点検は含まない。Issue ごとの記録にも同じ形で出る）・回数・コミットの数・作業場所（worktree とブランチ）・`HEAD`。続いて合格の条件ごとの判定表・やったこと・コミット・**選んだこと（Claude が自分で決めた点と戻し方）**・やらなかったこと・未採用の改善
3. 選んだことが違っていたら、コメントに書いてある戻し方で戻し、決定を「先に決めておくこと」に書いて `claude-failed`/`claude-done` を外す（次の回で対象になる）
4. 合格したものは確認して閉じ、push する
5. 中身のログは `Saved/IssueRun/<日時>/`（各回の JSON・報告ファイル・確認コマンドの出力）

## Issue の書き方

**ユーザーが書く文書・ゴールと合格の条件の書き方・確認コマンド・守るファイル・例・ラベルを付ける前の確かめは `Docs/Guides/Procedures/issue-goal-setting.md` が正。** ここには書かない（同じ説明が2か所にあると片方が腐る）。

ひな形は `.github/ISSUE_TEMPLATE/claude-run.md`。
