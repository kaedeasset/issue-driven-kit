# ゴールを決めて Issue に書く手順（無人の Claude に渡す前に）

ユーザーが書くもの・書き方・Issue への載せ方の正。無人で回す仕組み（スクリプト・ラベル・起動・止まらない仕組み）は `Docs/Guides/Working/issue-run.md`、回し方の中身（ゴール → 合格の条件 → 設計 → 実装 → テスト → 振り分け → 判定）は `.claude/skills/design-cycle/SKILL.md`。この文書は、その入口でユーザーがやることだけを書く。

2026-10-14 作成。公式の考え方（`Docs/Reports/2026/10/14/04`）と、このリポジトリの design-cycle を合わせた。

## 0. 流れ

```
① 決める（ユーザー）
   ↓
② 文書を書く … 大きいものは設計書。小さいものは要らない
   ↓
③ Issue を書く … 元の文書・合格の条件・確認コマンド
   ↓
④ 試す … pwsh Scripts\issue-run.ps1 -DryRun
   ↓
⑤ 起動 … pwsh Scripts\issue-run.ps1（時間帯は関係ない）。worktree の一覧が出るので、自分が作業していないものを選ぶ
   ↓
⑥ 確認（終わった後） … まとめ → Issue のコメント → 閉じる／直して出し直す
```

**一番大事なのは③の「確認コマンド」。** 無人の Claude は、確認コマンドが exit 0 になるまで終われない。逆に言えば、確認コマンドが通れば終わる。確認コマンドがゴールそのものになる、と思って書く。

## 1. どの文書を書くか

| やりたいことの大きさ | ユーザーが書くもの | Claude に任せられるもの |
|---|---|---|
| **小さい**（バグを1つ直す・データを数件足す・文言を直す） | Issue だけ。「元の文書」には今ある文書の該当の節を書く | 実装・テスト |
| **中くらい**（既存の設計書の1節を実装する） | Issue だけ。設計書のその節に合格の条件が書いてあれば、Issue はそれを指す | 実装・テスト |
| **大きい**（新しい機能・新しい画面・仕組みの変更） | **2回に分ける。** 1回目は「設計書を書く」Issue、終わったら設計書を読んで直す、2回目に「実装する」Issue | 1回目: 設計書の下書き／2回目: 実装・テスト |
| **方針が決まっていない**（やるかどうか・どちらの方式か） | Issue にしない。先に決める（決めたら `Docs/Guides/Decisions/` か `Docs/Guides-rpg/Decisions/` に書く） | — |

文書の置き場は CLAUDE.md の「置き場」のとおり（RPG は `Docs/Guides-rpg/`、ADV と共通の仕組みは `Docs/Guides/`）。設計の正はリポジトリの文書で、**Issue に設計を書かない**（同じ決定が2か所にできる）。

### 大きいものを2回に分ける理由

設計が正しければ、実装のやり直しが減る（design-cycle）。設計の良し悪しはユーザーが読まないと決まらないので、無人の回の間にユーザーの確認を1回はさむ。1回目で設計書、読んで直す、2回目で実装。

## 2. ゴールを1文で書く

「誰が・何を見て・どう判断するか」まで書く（design-cycle §1）。

| 悪い | 良い |
|---|---|
| ショップを作る | プレイヤーが村の店で武器を買い、所持金が減って装備の一覧に増えたのを見て、買えたと分かる |
| テストを強くする | `rpg-test.ps1` が、所持金が足りないときに買えないことも確かめる |
| 見た目を良くする | （無人には向かない。ユーザーが見て決める。→ 4 章） |

## 3. 合格の条件を書く

### 3.1 公式の3要素

1. **測れる終わりの状態が1つ** — テストの結果・終了コード・件数・ファイルがあるか
2. **確かめ方** — どのコマンドで、何が出たら合格か
3. **途中で変えてはいけないもの** — テスト・既存のデータ・ほかの機能

### 3.2 Issue に入れてよい条件・入れない条件

合格の条件には3種類ある（design-cycle §1）。**無人の Issue に入れるのは「機械」だけ。**

| 種類 | 例 | 無人の Issue では |
|---|---|---|
| 機械（コマンドで合否が出る） | テストが通る・ビルドが通る・CLI の出力が期待どおり・ファイルに節がそろっている | **合格の条件に入れ、確認コマンドで全部確かめる** |
| AI の判定（比べる相手と並べて判定） | ツクールと並べて見た目が以上か | 合格の条件に入れない。「やらないこと」に「判定はしない。撮影と記録まで」と書く |
| ユーザーの判定（実感） | 遊んで面白いか・読みやすいか | 合格の条件に入れない。終わった後にユーザーがやる |

機械で測れない条件を入れると、Claude は自分で「合格」と書くしかなくなる。それが公式の言う一番の失敗（早すぎる勝利宣言）。

### 3.3 箇条書きと確認コマンドを対応させる

箇条書きの1行ずつが、確認コマンドのどこかで確かめられるようにする。確かめられない行は書かない（書くなら「やらないこと」へ）。

## 4. 確認コマンドを書く

Issue の「## 合格の条件」の中に ```` ```pwsh ```` で書く。**リポジトリの直下で実行され、exit 0 なら合格。** Claude が「合格」と報告しても、これが通るまで終われない。

### 4.1 既存の入口（そのまま呼べる）

| 対象 | コマンド | 合格 |
|---|---|---|
| RPG の CLI と core（UE を使わない。自分が UE を使っている間でも回せる） | `pwsh -NoProfile -File Scripts/rpg-test.ps1` | exit 0（最後の行 `Result: PASS`） |
| ADV の作品（L1） | `pwsh -NoProfile -File Scripts/adv-test-summary.ps1 -Work Game/adv` | exit 0（L1 の終了基準を満たした） |
| UE のビルド（エディタを組み立てる）。**最終段階の Issue だけ（4.3）** | `Build.bat kaedevnEditor Win64 Development -project=<worktree>/kaedevn.uproject`（4.3 の書き方） | 出力に `Result: Succeeded` がある。**終了コードは見ない**（失敗でも 0 を返すことがある。`worktree-parallel-development.md`） |

ほかの入口は `Docs/Guides-rpg/Working/rpg-scripts-and-tests.md`（RPG）と `Docs/Guides/Procedures/adv-test-procedure.md`（ADV）。

### 4.2 その Issue だけの確かめを書く

既存のテストに無いことは、確認コマンドの中に直接書く。**Issue の中に書いたものは Claude が書き換えられない**ので、一番固い。

```pwsh
# 例: CLI の出力を確かめる
$out = & Tools/rpg-cli/build/Release/kaede-rpg.exe shop list --json | ConvertFrom-Json
if ($out.Count -lt 3) { Write-Host "店の品が 3 未満: $($out.Count)"; exit 1 }

# 例: 文書に必要な節がそろっている
$t = Get-Content 'Docs/Guides-rpg/Working/rpg-shop-design.md' -Raw
foreach ($h in '## 0. ゴールと合格の条件', '確認コマンド') {
    if ($t -notmatch [regex]::Escape($h)) { Write-Host "無い: $h"; exit 1 }
}

exit 0
```

- 落ちたときは `Write-Host` で理由を出す。その出力の末尾が Claude に渡り、次に何を直すかの手がかりになる。
- 最後は `exit 0`。
- 例の CLI の引数・設計書の名前は架空。実在のものに直して書く。

### 4.3 UE の組み立ては最終段階だけ

**確認コマンドに UE の組み立て・エディタ・L4（空のプロジェクト）を入れない。** ゲームの中身は UE を使わない C++ に分けてあり、`rpg-test.ps1`・`adv-sim` が差分だけ組み立てて試す（UE と同じ警告をエラーにしてある）。UE の組み立ては main に取り込むとき・梱包するときに 1 回やる（CLAUDE.md: フルビルドと全テストは main）。そこで落ちたら、その Issue に戻す。

- 2026-10-15 の実測: 確認コマンドに UE の組み立てを入れた #7 は、1 回目だけで 45 分（組み立て 19 分）。足したのはソースの 1 行目のコメントだけで、`git diff` で確かめれば済んだ。
- **コメントだけの変更**（頭書き・説明）は組み立てない。「変えたのはコメントの行だけ」を `git diff` で確かめる。
- 入れてよいのは、**UE で動くことそのものがゴールの Issue**（L4 の仕組みを作る・梱包を変える）だけ。そのときも組み合わせは 1 回にまとめる（例: 製品を全部入れた 1 回。製品の間の依存は境界の検査がソースで確かめる）。書き方:

```pwsh
$log = & 'D:/EpicGames/UE_5.8/Engine/Build/BatchFiles/Build.bat' kaedevnEditor Win64 Development "-project=$PWD/kaedevn.uproject" 2>&1 | Out-String
if ($log -notmatch 'Result: Succeeded') { Write-Host 'ビルド失敗'; exit 1 }
```

### 4.4 変えさせたくないファイルを守る

**確認コマンドに出てくる、git が管理しているファイルは、自動で守られる。**（ビルドで作り直される exe などの管理外のファイルは守られない） 開始時の中身から変わっていたら（消しても）合格にならない。テストのスクリプトや、期待値のデータを Claude が都合よく直すのを防ぐ（公式の「テストを書き換えない」）。

確認コマンドで使わないが守りたいファイルは、コメントの行にパスを書けば守られる:

```pwsh
# 守る: Tools/rpg-cli/tests/fixtures/shop.json
# 守る: Docs/Guides-rpg/Working/rpg-maker-tool-detailed-design.md
pwsh -NoProfile -File Scripts/rpg-test.ps1
```

- 守れるのは**ファイル単位**。フォルダを書いても守られない。フォルダごと変えさせたくないときは、確認コマンドの最後で `if (git status --porcelain -- <フォルダ>) { Write-Host '<フォルダ> を変えている'; exit 1 }` と見る（#101）。
- **テストそのものを直す Issue** では、そのテストのファイルを確認コマンドに書くと直せなくなる。確認コマンドは別の入口（それを呼ぶ上位のスクリプトなど）から呼ぶ。
- **直させるファイルは、確認コマンドの中で変数を通して指す**（`$tests = 'Tools/rpg-cli/tests'` → `"$tests/play-tests.cpp"`）。パスをそのまま書くと自動で守られ、直せなくなる（#26 の書き方。「直すべきファイルは変数で指す」とコメントを残す）。
- **変数に入れるのはフォルダーまで**にする。`$man = 'Docs/…/manual.md'` のようにファイルのパスを丸ごと代入しても、そのパスは確認コマンドにそのまま書いてあるので守られる（説明書を直す Issue が 4 回とも合格できなかった）。
- **作業で直す必要のあるファイルを「守る」に入れない。** #7 は、旧い名前を消す作業なのに、その名前が残る設計書を守っていて、4 回とも合格できなかった。
- どのファイルが守られるかは `-DryRun` の「守るファイル」に出る。作ったら「守るファイル」の行を**切らずに全部読み**、直させるファイルが 1 つも入っていないことを確かめる。
- **deny のパス（直下の `CLAUDE.md`・`.claude/`・`Docs/InSpecs/`・`Server/kaede-rpg-server/CLAUDE.md`）は合格の条件に入れない。直す必要があれば人が直す。** 無人の回の設定（`.claude/issue-run/settings.json`）の deny が書き換えを断るので、何回回しても満たせない（公開のキットで、直下の `CLAUDE.md` の 1 行を消す条件が 4 回とも満たせず、人が直して合格した）。変えないことを確かめるために書くのはよい。`-DryRun` は、合格の条件（箇条書きと確認コマンド）に deny のパスに当たる語があれば「deny のパス: …」の行で知らせる（頭にフォルダーが付いた `Templates/NewWork/CLAUDE.md` などは当たらない）。

## 5. Issue を書く

GitHub の「New issue」でひな形「Claude に無人で進めさせる」を選ぶ（スマホのアプリからも同じ）。ひな形が出ないうちは手で書き、ラベル `claude-run` を付ける。

| 欄 | 書くこと | 必須 |
|---|---|---|
| タイトル | 何をするかを1行 | ○ |
| やること | ゴールを1文（2 章）。**90 分 × 4 回で終わる大きさ**（実測は 1 件 30 分〜1 時間。5.1） | ○ |
| 元の文書 | 設計書・計画書のパスと節。小さいものは今ある文書の該当の節 | ○ |
| 合格の条件 | 箇条書き（3 章）＋ ```` ```pwsh ```` の確認コマンド（4 章） | ○（どちらかが無いと起動しない） |
| 前提 | この Issue の前に済んでいるべき Issue（`- #1` のように）。前提が合格（`claude-done`）か閉じられるまで始まらない。始める直前に見るので、**同じ実行の中で前の段が合格すれば、続けて次の段が始まる** | 任意 |
| 先に決めておくこと | Claude が迷いそうな点。書かなかった点は Claude が「git で戻せて範囲が小さいほう」を選び、報告に選んだことと戻し方を書く | 任意 |
| やらないこと | 範囲の外。見た目の判定・ほかの機能・UE の組み立て（最終段階でやる。4.3） | 任意 |

### 5.1 大きさの目安

- 1つの Issue に、確認コマンドで確かめる「終わりの状態」は1つか2つ。
- 「計画書の §4 を全部」ではなく「§4.2 だけ」。
- 1回の起動の上限は 90 分 × 4 回。それで終わらない大きさなら分ける。
- **1件にかかる時間（2026-10-14 の実測）:** UE のビルドとテスト（確認コマンドで5つのテストを回す）が入る段は **約1時間**（Claude の作業 約47分＋スクリプトの再確認 約13分。分割の S1・Issue #2）。確認が軽い段は約30分（S0・#1）。
- **積む件数の目安:** 使える時間で決める。7〜8時間なら **6〜8件**、数時間なら **2〜3件**。前提でつないでおけば、途中で1件つまずいても後ろは前提待ちで止まるだけなので、多めに積んでよい。少ないと、終わった後の時間が空く。

### 5.1.1 段を順につなぐ（1 回の実行で何段も進める）

大きな作業を段に分けたら、2 段目から先の Issue に「## 前提」で前の段を書き、全部に `claude-run` を付けておく。番号の小さい順に回るので、1 段目が合格すると同じ実行の中で 2 段目が始まる。1 段目が合格しなければ、2 段目は「前提待ち（WAITING）」として何もせずに残る。

- 後の段の確認コマンドが「前の段と同じ結果か」を比べるなら、前の段に**比べるための記録を機械で読める形（JSON）で残させる**（例: 分割の S0〜S1〈Issue #1・#2〉）。
- 前の段の Issue の最後に「## 次の段」を書いておくと、後で読むとき流れが分かる（スクリプトは読まない）。
- 設計書を書く Issue の合格の条件に「実装を分けた束（K1・K2…）の一覧と、束ごとの確認コマンドの案」を入れておくと、2 回目以降の Issue がその束を 1 つずつ指せる（#20 → #25〜#27「#20 の束 K2」）。設計書にテストの名前の表を書かせるなら、束は印の文（「（K2）」など）に混ぜず**「束」の列**に書かせ、見出しの行を `| 束 | テストの名前 | 何を確かめるか |` の形で確認コマンドから確かめる。実装の Issue は列の値で行を絞り、**読めた本数を Issue に書いた数と比べる**（`> 0` にしない。印の書き方が `（K2）` と `（束 K2）` で揺れて、読めなかった名前が確かめから漏れた例が公開のキットにある）。
- 人が手でやるもの（本番への配備・別の PC での確認など）も Issue にしてよいが、`claude-run` を付けない（#17・#44）。

### 5.2 自分が UE を使っている間に回すとき

時間帯は関係ない（2026-10-15 に `-Mode night/day` を廃止）。ふつうの Issue は CLI だけで確かめる（4.3）ので、自分が UE を使っている間でも回せる。UE を使うのは最終段階の Issue だけで、UE は同時 1 本なので、それは自分が UE を使っていないときに回す（使っている間は、ビルドの要る条件を「未判定」にして再開を待つ）。

作業場所は、どちらでも**自分が作業していない既存の worktree** を選ぶ（起動時の一覧から）。

## 6. 例

どれも書き方の例。CLI の引数（`shop buy` など）と設計書の名前（`rpg-shop-design.md`）は架空なので、実在のものに直して書く。

### 6.1 小さい — CLI のバグを直す（UE を使っている間でもよい）

````
タイトル: RPG CLI: 所持金が足りないのに店で買えてしまう

## やること
所持金が値段より少ないとき、店で買えないようにする。

## 元の文書
Docs/Guides-rpg/Working/rpg-maker-tool-detailed-design.md の店の節

## 合格の条件
- 所持金が足りないとき、買う操作が失敗し、所持金と持ち物が変わらない
- 既存の RPG のテストが全部通る

```pwsh
# 守る: Tools/rpg-cli/tests/fixtures/shop.json
pwsh -NoProfile -File Scripts/rpg-test.ps1
if ($LASTEXITCODE) { exit 1 }
# この Issue だけの確かめ（コマンドと引数は実在のものに直す）
$r = & Tools/rpg-cli/build/Release/kaede-rpg.exe shop buy --gold 10 --item sword --json | ConvertFrom-Json
if ($r.ok) { Write-Host '所持金 10 で剣が買えてしまった'; exit 1 }
exit 0
```

## やらないこと
- UE の組み立て（最終段階でやる。4.3）
````

### 6.2 大きい・1回目 — 設計書を書かせる

````
タイトル: RPG 店の機能の設計書を書く

## やること
店の機能（買う・売る・品ぞろえ）の設計書を、design-cycle の形で書く。

## 元の文書
Docs/Guides-rpg/Working/rpg-maker-tool-detailed-design.md（今の仕様）
.claude/skills/design-cycle/SKILL.md（設計書の形）

## 合格の条件
- 設計書が Docs/Guides-rpg/Working/rpg-shop-design.md にある
- §0 にゴール・合格の条件の表・実装の Issue に使う確認コマンドの案がある
- 事実（今の CLI の出力・データの形）を確かめた根拠がある

```pwsh
$d = 'Docs/Guides-rpg/Working/rpg-shop-design.md'
if (-not (Test-Path $d)) { Write-Host '設計書が無い'; exit 1 }
$t = Get-Content $d -Raw
foreach ($h in '## 0.', 'ゴール', '合格の条件', '確認コマンド', '根拠') {
    if ($t -notmatch [regex]::Escape($h)) { Write-Host "無い: $h"; exit 1 }
}
exit 0
```

## やらないこと
- 実装（2回目の Issue でやる）
````

終わったら設計書を読み、直したいところは自分で直すかコメントに書く。良ければ設計書の §0 の確認コマンドの案を使って、2回目の「実装する」Issue を書く。

### 6.3 大きい・2回目 — 実装する

````
タイトル: RPG 店の機能を実装する（設計書 §1〜§3）

## やること
設計書どおりに店の機能を実装し、設計書の合格の条件を全部満たす。

## 元の文書
Docs/Guides-rpg/Working/rpg-shop-design.md の §1〜§3

## 合格の条件
- 設計書 §0 の合格の条件のうち、機械で測れるもの全部
- 既存の RPG のテストが全部通る

```pwsh
# 守る: Docs/Guides-rpg/Working/rpg-shop-design.md
pwsh -NoProfile -File Scripts/rpg-test.ps1
if ($LASTEXITCODE) { exit 1 }
exit 0
```

## やらないこと
- UE の組み立て（main に取り込むときにやる。4.3）
- 見た目の判定（後でユーザーがやる。撮影まではしてよい）
````

設計書を「守る」に入れると、Claude は実装の都合で設計書を書き換えられない。設計を変えたくなったら合格にならず、報告の「やらなかったこと」に理由が残る（設計の直しはユーザーが決める）。

## 7. ラベルを付ける前の確かめ

- [ ] やることが1文で、90 分 × 4 回で終わる大きさ

## 8. 終わった後の確認

1. `Docs/IssueRuns/issue-NNNN.md`（Issue ごとの記録。番号を 4 桁に。いちばん下の節がこの回）
2. 合格した Issue のコメント: 判定表・**選んだこと（Claude が自分で決めた点と戻し方）**・やらなかったこと
   - 選んだことが違っていたら、コメントの戻し方で戻し、「先に決めておくこと」に正しい決定を書いて、ラベル `claude-done` を外す（次の回でやり直す）
   - 良ければ閉じて push する
3. 合格しなかった Issue（`claude-failed`）: コメントの理由を見る
   - 合格の条件か確認コマンドが無い → 書き足す
   - 回数切れ → 大きすぎる。分ける
   - 守るファイルを変えようとした → 設計か確認コマンドが実情に合っていない。直す
   - 「報告が判定不能（合格の条件が両立しない）」 → 作る側をどう直しても合格できないと Claude が実行結果で示した。コメントの「両立しない条件」（ぶつかる 2 つ・根拠・直し方の推し）を読み、Issue の条件か守るファイルを直す
   - 「最後の返答」が `You've hit your session limit` → 中身の不合格ではない。条件を変えずに `claude-failed` を外して出し直す
   - 権限で断られて 1 か所だけ書けなかった → 報告に用意された中身を手で入れてコミットし、出し直すか手で閉じる
   - 直したらラベル `claude-failed` を外す。**何を直したか・条件を変えたかをコメントに残す**（「## 対応（日時・ユーザーのセッションから）」に、直したこと・「本文の合格の条件は変えない」・次にどうするか）
4. 閉じるときは「合格（claude-done）を確認して閉じる（YYYY-MM-DD ユーザー指示）」とコメントしてから閉じる
5. 「未採用の改善」に良いものがあれば、新しい Issue にする（自動では仕事にならない）
