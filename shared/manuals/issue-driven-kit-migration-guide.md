# Issue 駆動キット 移行ガイド — 入れたキットを新しい版に上げるときに、自分のリポジトリで直すこと

> Generated by Claude Opus 5.5 — 2026年11月3日

キットは、脚本や設定の形を変えたとき**古い形を残さない**（後方互換を作らない）。古い形のまま上げると、テストの入口や点検が `FAIL`・`NG` で止まり、直し方を出す。このガイドは、その直し方を書く。版が上がって形が変わるたびに書き足す。

キットの上げ方そのもの（`git pull` と `--update`）は、導入ガイド [`issue-driven-kit-install-guide.md`](issue-driven-kit-install-guide.md) の手順 8。

---

**この版（2026-11・Node 版）：テストの入口の設定を `.issue-kit/config.json` に移す。**

## 1. この版で変わること

| 所 | 前 | この版から |
|---|---|---|
| テストの入口の設定の置き場 | `package.json` の `issueKit` の欄（`testRunner`・`testFiles`） | **`.issue-kit/config.json` の `test` の欄**（`runner`・`files`・`command`・`resultDirs`・`filterArgs`） |
| 欄が無いとき | vitest で回す（既定） | **既定の値は無い**。ファイルが無い・読めない・形が違えば `Result: FAIL`（直し方を出す） |
| 古い欄 | — | **読まない**（`package.json` の `issueKit` は残っていても使われない） |
| 回せる道具 | vitest・`node --test` | vitest・`node --test`・**`command`**（決めたコマンドを起動し、JUnit の XML を読む。.NET・Java などのテストも同じ入口で回せる） |
| 数え方 | vitest は `<testsuites>` の属性を読んでいた | どの道具でも `<testcase>` を 1 つずつ数える（決まりの正はキットの仕様 [`issue-run-spec.md`](../spec/issue-run-spec.md) の 11 章） |
| 無人の回 | `.issue-kit/` を書き換えられた | 実行用の設定の deny で `.issue-kit/` の書き換えを断る（テストの設定を「通る XML を書くだけ」に変えて合格を作れない）。Issue の合格の条件に `.issue-kit/` を直させる条件を入れない |
| 入れる脚本 | — | `.issue-kit/config.json` のひな形（`{ "test": { "runner": "vitest" } }`）を写す。利用先が書き換える物として扱い、`--update` で上書きしない |

## 2. 移す手順

| 順 | すること |
|---|---|
| 1 | キットを `git pull` し、自分のリポジトリで `--update` で入れ直す（導入ガイドの手順 8）。`.issue-kit/config.json` が無かったリポジトリには、ひな形（vitest）が写る |
| 2 | `.issue-kit/config.json` を、いままでの `issueKit` の欄に合わせて書く（下の表）。`issueKit` の欄が無かった（vitest で回していた）なら、写ったひな形のままでよい |
| 3 | `package.json` から `issueKit` の欄を消す（もう読まれない。残すと、どちらが正か分からなくなる） |
| 4 | 3 章のとおりに確かめ、コミットする（`.issue-kit/config.json` と `package.json` を一緒に） |

| 前（`package.json`） | この版から（`.issue-kit/config.json`） |
|---|---|
| 欄が無い（vitest） | `{ "test": { "runner": "vitest" } }` |
| `"issueKit": { "testRunner": "vitest" }` | `{ "test": { "runner": "vitest" } }` |
| `"issueKit": { "testRunner": "node", "testFiles": "tests/*.test.mjs" }` | `{ "test": { "runner": "node", "files": ["tests/*.test.mjs"] } }`（`testFiles` が文字列なら配列にする） |
| `"issueKit": { "testRunner": "node", "testFiles": ["a.test.mjs", "b.test.mjs"] }` | `{ "test": { "runner": "node", "files": ["a.test.mjs", "b.test.mjs"] } }` |

## 4. .NET と Java の設定の例

言語が Node でないリポジトリでは、`runner` を `command` にし、テストを回すコマンドと、結果の JUnit の XML が出るフォルダーを書く。キットの脚本を動かすのに Node.js 22.14.0 は要るが、`package.json` は要らない。

| 道具 | `.issue-kit/config.json` |
|---|---|
| .NET（xUnit と `JunitXml.TestLogger`） | `{ "test": { "runner": "command", "command": ["dotnet", "test", "--logger", "junit;LogFilePath=.issue-run/test-results/raw/{assembly}.xml"], "resultDirs": [".issue-run/test-results/raw"], "filterArgs": ["--filter", "DisplayName~{filter}"] } }` |
| Java（Maven Wrapper・Surefire・Failsafe） | `{ "test": { "runner": "command", "command": ["mvnw.cmd", "-q", "verify"], "resultDirs": ["target/surefire-reports", "target/failsafe-reports"] } }`（Mac は `./mvnw`） |

- 設定は 1 つなので、Windows と Mac の両方で回すリポジトリでは、`command` の先頭を両方で動く物にする（Java の `mvnw.cmd` と `./mvnw` は書き分けられない。PATH にある `mvn` を使うなど）。
- **.NET の例は、まだ実測していない。** `dotnet test` の VSTest の方式の物で、Microsoft.Testing.Platform の方式を選んだプロジェクトでは `--logger` を受け付けない。`LogFilePath` の相対パスの基準（どのフォルダーから見るか）と `{assembly}` の置き換えも確かめていない。試して違えば、`command` と `resultDirs` をそのプロジェクトで実際に XML が出る所に合わせる。
- .NET の `requireTests` の名前は、xUnit の `DisplayName` が `<testcase>` の `name` に出る形で書く（キットは `name` を読むだけ）。
- `filterArgs` の `{filter}` には `--filter` の値をそのまま入れる。dotnet の `--filter` で意味を持つ字（`( ) & | = ! ~ ,`）は `\` で逃がす（テストの名前に使わないのが簡単）。
- Java（Maven）は名前でなくクラスとメソッドで絞るので、`filterArgs` を書かない。`--filter` は使わず、全部を回して `requireTests` で名前を見る。
- Windows で `command` の先頭が `.cmd`・`.bat`（`mvnw.cmd` など）のときは `cmd.exe` を通して起動する。引数に `%` と `"` は使えない（使うと起動せずに FAIL）。
- 結果の XML は UTF-8 で書かせる（UTF-16 は読めず、0 件で FAIL になる）。
- `command` は `--file` を使えない（ファイルの指定は道具ごとに違う）。名前で絞るなら `filterArgs` を書く。
- 前の回の XML が `resultDirs` に残っていても読まない（起動の前後で一覧を比べ、この回で新しくできた物と、更新時刻か大きさが変わった物だけを読む）。キットはそのフォルダーを消さない。

## 5. 古い形のまま上げたとき

`.issue-kit/config.json` を書かずに上げると、テストの入口は道具を起動せずに止まる。

| 出る物 | 意味 | 直し方 |
|---|---|---|
| `Result: FAIL (.issue-kit/config.json が無い。テストの道具を書く（例 { "test": { "runner": "vitest" } }）。古い形の package.json の欄は読まない（移す手順はキットの移行ガイド）)` | 設定が無い。`package.json` の `issueKit` は読まれない | 2 章の手順で書く |
| `Result: FAIL (.issue-kit/config.json が JSON として読めない…)`・`（… に test の欄が無い…）`・`（… の test.runner は vitest・node・command のどれか…）`・`（… の test.files が無い…）` など | 設定の形が違う | 出力の直し方のとおりに直す（欄の意味は 1 章の表と、版の手順書 `docs/guides/procedures/node-test-procedure.md`） |
| 点検の `NG   テストの仕組み` | 上と同じ理由 | 同じ |
| 確認コマンドの `runTests` が `NG  テスト 全部: Result: FAIL (.issue-kit/config.json が無い…)` | 無人の回でも同じに落ちる。無人の回は `.issue-kit/` を書き換えられないので、合格できないまま回数を使う | 無人の回を回す前に、会話で 2 章を済ませる |
