# README をポートフォリオ向けにする設計

直下の `README.md` を、初めて見る人（採用の担当・面接の人・キットを使うか迷う人）が 1 画面半で「何ができるか・どう実現しているか・Claude Code をどう使ったか」を分かり、詳しい文書を読みたくなる入口に書き直す。

## 1. ゴール

初めて見る人が README だけを読んで、次の 3 つを言えるようになる。細かい値や手順は README に書かず、リンク先の文書に任せる。

1. 何ができるか（Issue にラベルを付けると、Claude Code が合格するまで無人で進める）
2. 実績（数字）
3. どう実現しているか（AI に任せたときの困りごとと、その解き方）

## 2. 決めたこと

| 決めること | 決めた内容 |
|---|---|
| 長さ | 120 行以内（ファイルを改行で分けた行の数）。各節は 1〜3 行か表 1 つにし、最後に「続きはこの文書」のリンクを置く |
| 言語 | 本文は日本語。タイトルの直後に英語の要約（節 `## Summary (English)`、3〜4 行） |
| 用語 | 一般的な言い方にする（ラベル・スクリプト・テスト・確認コマンド）。キットの中の独自の言い方（札・脚本・試験）は、残す表の中も含めて README に使わない |
| リンクの書き方 | 文書の名前を並べず、その文書で分かる問いを添える（例：「AI が途中で止まらないのはなぜ？ → issue-run.md」）。リポジトリの中の文書は相対リンク、GitHub の Issue の一覧は絶対 URL |
| 日付つきの現況 | 今の「いまの状態（2026-10-28）」の囲みは README から外す。確かめた OS は「版を選ぶ」の表の「動く OS」の欄に書き、Node 版の欄から導入ガイドの `#確かめた版` へリンクする |
| 細かい値 | 回の数・時間の上限・押し返しの回数などは README に書かない（値が変わっても README を直さずに済むように） |
| 実績の数字 | 4 章の値をそのまま写す。数えた日を行ごとに添え、更新し続ける現況ではないと分かるようにする。数え直すのは会話の中で（元のリポジトリは private で、無人の回からは見えない）。数え直したら 4 章と README の両方を直す |
| private の中身 | 元の Unity のリポジトリと Unreal Engine のリポジトリは private。README には数字と、作った物の種類だけを書く。Issue の題名・コード・PC の中のパスは書かない |

## 3. 節の順と中身

| 順 | 節 | 中身 |
|---|---|---|
| 1 | タイトル＋1 行 | 「GitHub Issue に合格の条件と確認コマンドを書いてラベルを付けると、Claude Code が合格するまで設計・実装・テストを無人で回す」。バッジは付けない（外のサービスに頼らない） |
| 2 | `## Summary (English)` | 「タイトルの 1 行」「実績」「Issue 駆動を支える技術」の要約を英語で 3〜4 行 |
| 3 | `## 実績` | 4 章の数字。このリポジトリと rpg-online-cloudflare の合格した Issue の一覧（`https://github.com/<owner>/<name>/issues?q=label%3Aclaude-done`）へのリンク |
| 4 | `## Issue 駆動を支える技術` | 5 章のとおり |
| 5 | `## 設計で決めたこと` | 3 行。「一つの決まりは一か所に書く（仕様 → 2 つの版 → 見本）」「合否は AI の言葉ではなく確認コマンドで決める」「npm の依存を持たない」。基本設計へのリンク |
| 6 | `## 版を選ぶ` | 今の表を残し、用語を言い換える（脚本 → スクリプト）。Node 版の「向いているリポジトリ」は基本設計の版の表（Node 版の行）に合わせる（Node.js＋TypeScript のほか、テストの結果を JUnit の XML に書ける .NET・Java など）。**入れ方の行は外す**（入れ方は「使ってみる」の一か所） |
| 7 | `## 使ってみる` | 2 つの版の入れ方の 1 行ずつ（`--dry-run` つき）と、導入ガイドへのリンク |
| 8 | `## 中身` | 今の表を 5〜6 行に縮める（仕様・2 つの版・共有の説明書・設計・テスト）。テストの行に `npm test` を書き、今の節「キット自身の試験」は消す（`KIT_UNITY_REFERENCE` の説明は作者の PC だけの話なので README から外す） |
| 9 | `## 作者・ライセンス` | 役割の分担（人：ゴールと合格の条件・確認・push。Claude Code：設計からコミットまで）を 1 行。MIT。今の文のうち「このリポジトリは公開です。作者の private のリポジトリの中身は入れていません（抜いた物は `shared/SOURCE.md`）」と、記録の番号（「記録 22/01」「P54」）の注は残す。「開発の途中の履歴は private に残しています（Issue #1〜#5）」の文は、今は Issue が公開なので消す |
| 末尾 | — | 「この文書は Claude Opus 5.5 が生成しました…」の行は残す |

## 5. 「Issue 駆動を支える技術」の節

AI に仕事を任せると起きる 3 つ（途中で止まる・勝手に「できた」と言う・やってはいけない操作をする）を最初の 1〜2 行で書き、その後に次の 3 つを置く。

1. **1 件の流れ**：Mermaid の図 1 つ。箱は 6〜7 個まで（Issue にラベル → スクリプトが Claude Code を起動 → 設計・実装・テスト → スクリプトが確認コマンドで判定 → 合格ならラベル `claude-done`／不合格なら続きから再開／決まった回数で合格しなければ `claude-failed` にして次の Issue へ）。その下に「人がやるのは、合格の条件を書くことと、結果を見て閉じる・push すること」の 1 行。
2. **困りごとと解き方の表**：列は「困りごと」「解き方」「使っている Claude Code の機能」。行は次の 7 つ。

   | 困りごと | 解き方 | 機能 |
   |---|---|---|
   | 人がいないと進まない | スクリプトが Issue を 1 件ずつ取り、Claude Code を無人で起動する | Headless（`claude -p`） |
   | 区切りで返答を終えて止まる | 合格の報告が書かれるまで、返答を終えさせない | Hooks（Stop hook） |
   | 合格していないのに「できた」と言う | 合否はスクリプトが確認コマンドを回して決め、落ちたら出力を付けて同じ会話を続きから再開する | `--resume` |
   | テストのほうを書き換えて合格にする | 判定に使うファイルの指紋を開始時に取り、変わっていたら合格にしない | （スクリプト） |
   | push・削除など危ない操作をする | 設定で必ず断り、確認の画面も出さない | Settings（deny）・`--permission-mode auto`・`--permission-prompts none` |
   | 質問して待ち続ける | 質問の道具を外し、「戻せるほうを選んで、選んだことを書く」決まりを渡す | `--disallowed-tools`・指示文と CLAUDE.md |
   | 設定が効いているか分からない | スクリプトが起動前に `claude -p` で試し、Stop hook が呼ばれることと deny が効くことを確かめてから始める | （スクリプト） |

   表の下に `docs/guides/working/issue-run.md` と `shared/spec/issue-run-spec.md` へのリンク。
3. **人の側を支える道具の表**：スキル `github-issue`（会話で Issue を書く）・スキル `design-cycle`（ゴールから合格判定まで）・worktree のレーン（並べて動かし朝に同期）・CLAUDE.md（短く保ち、作業ごとの文書へ振り分ける）。表の下に `docs/guides/working/issue-driven-development.md` へのリンク。

## 6. 変えないもの

- README 以外の文書（導入ガイドなど）は変えない。「札」「脚本」「試験」の言い方が残る文書の書き換えは別の作業にする。
- キットの部品（`editions/`・`shared/`・`scripts/`）と試験は変えない。

## 7. 合格の条件

1. `README.md` が 120 行以内
2. 節の見出し（`## Summary (English)`・`## 実績`・`## Issue 駆動を支える技術`・`## 設計で決めたこと`・`## 版を選ぶ`・`## 使ってみる`・`## 中身`・`## 作者・ライセンス`）がこの順にある
3. Mermaid の図が 1 つある
4. 4 章の数字（合格の数・Issue の数・コミットの数）が書いてある。「13 件」の文が無い
5. 5 章の表の機能の語（`claude -p`・Stop hook・`--resume`・deny）が書いてある
6. 「札」「脚本」「試験」「いまの状態」の語が無い。PC の中のパス（ドライブ名・`/Users/`）が無い
7. README の中の相対リンクの先のファイルが全部ある（`#` より後ろの見出しは見ない）
8. キットの試験が全部通る

確認コマンドでは README のパスをそのまま書かない（そのまま書くと守るファイルになり、直せなくなる。仕様 2.3）。
