## 1. 目的・背景

生成AIによるIssue駆動開発が、ブラウザアプリだけでなく、**WindowsネイティブGUI、業務DB、帳票、ファイル入出力、APIサーバー、インストーラー**まで含む新規開発で成立することを示す。既存システムの互換性、コード移行、保守は対象としない。

アプリの機能要件に加え、Issue単位の受入条件、ビルド/テストの自動実行、失敗時の再試行と人間のレビューを記録することを目的とする。

## 2. システム概要・利用者

- 仮称：SalesFlow Windows。
- **クライアント**：Windows 11デスクトップ、C#/.NET 10、WinUI 3、Windows App SDK。マウスとキーボードに対応。
- **サーバー**：ASP.NET Core Web API、.NET 10、REST/JSON、PostgreSQL、Entity Framework Core。
- **通信**：HTTPS。オフライン操作・ローカルDBへの本業務保存は実装しない。
- **役割**：管理者、営業担当、閲覧担当。
- **データ**：架空の顧客と商品を用いる。業務日時はUTC保存/JST表示、通貨はJPY。

## 4. 対象外

Windows 10対応保証、macOS/Linuxクライアント、オフライン同期、複数倉庫、配送・電子決済、会計ソフト連携、複雑な税区分、バーコード機器、Excelネイティブ書式、電子署名・適格請求書制度の実務完全準拠、AD/Entra ID SSO。追加時は別Issueで要件変更する。

## 5. 主要業務ルール

| ID | 規則 |
|---|---|
| NET-BR-01 | 商品・顧客コードは一意。無効化済みを新規受注に利用不可、過去取引は保持 |
| NET-BR-02 | 明細：数量1～9999、単価0～9,999,999円、受注あたり100行以内。金額は整数円で保存 |
| NET-BR-03 | `subtotal=sum(unitPrice×qty)`、税=`floor(subtotal×0.10)`、総額=subtotal+税。10%は**テスト用固定モデル** |
| NET-BR-04 | 受注状態：DRAFT→CONFIRMED→INVOICED、DRAFT/CONFIRMED→CANCELEDのみ許可 |
| NET-BR-05 | 確定で在庫減算、請求前取消で在庫復元。API再送・二重クリックでも二重更新しない |
| NET-BR-06 | 請求書は1受注につき1件。発行後の金額・明細は変更不可 |
| NET-BR-07 | 他端末から更新されたデータを古い画面状態で上書きせず、競合として再読込を案内 |
| NET-BR-08 | CSV取込は行単位エラーを一覧表示。検証でエラーがある場合、全体反映を行わない（MVPは全件原子性） |
| NET-BR-09 | viewerは閲覧・出力のみ、operatorは受注操作と請求、adminはマスター変更・在庫調整を含む全操作 |
| NET-BR-10 | PDFの金額、請求番号、日時、顧客名はDB保存済みの請求スナップショットを基準とする |

## 7. 受入テスト条件

| ID | ケース | 期待結果 |
|---|---|---|
| NET-AC-01 | 商品P001=1000円・在庫10、P002=350円・在庫3、受注数量2・1 | 税抜2350/税235/税込2585円を画面・APIで一致 |
| NET-AC-02 | 上記受注を確定 | 在庫P001=8/P002=2、状態CONFIRMED |
| NET-AC-03 | 残り在庫2のP002を3個確定 | エラーを表示。全商品在庫は不変 |
| NET-AC-04 | 確定受注を取消 | 在庫が戻り、2回目の取消で増えない |
| NET-AC-05 | 確定受注から請求発行を2回押下 | 請求書は1件のみ、合計2585円 |
| NET-AC-06 | 請求後の受注取消 | 操作拒否、請求/在庫変化なし |
| NET-AC-07 | 古いversionのデータを別端末で更新 | 409相当、競合通知が表示される |
| NET-AC-08 | viewerがPOSTでマスター更新 | 403、DB不変 |
| NET-AC-09 | 重複商品コードを含むCSVを投入 | 行別エラー、取り込み0件、DB不変 |
| NET-AC-10 | 正常CSVを取込み後、商品一覧と出力結果を照合 | 行数とフィールドが一致（UTF-8 BOMの有無などは設計で規定） |
| NET-AC-11 | 請求書PDFを生成 | 請求番号、顧客、明細、税抜・税・税込、発行日時が含まれる |
| NET-AC-12 | アプリインストール・起動・削除 | 標準Windows 11環境で手順通り成功、残留機密なし |
| NET-AC-13 | サーバー切断中の保存 | 明確なエラーと再試行導線。処理が成功したか不明なときは状態を再照会する |
| NET-AC-14 | サインアウト後に再操作 | 認証を要求し、認証情報を機密ログに残さない |
| NET-AC-15 | 初期化→シード→自動テストを2回実行 | 同じ合格結果、終了コード0 |

## 8. 非機能要件

| 分類 | 要件・検証 |
|---|---|
| OS | Windows 11 x64（初期対象）。WinUI 3/Windows App SDKの対応バージョンをロック |
| 性能 | 固定データ受注1万件で一覧初回表示3秒以内を目標（実機と条件を記録し未達を報告） |
| 操作性 | 保存中はボタン停止、Enter/Tabで移動、確認ダイアログ、キャンセル可能な取得処理 |
| 障害対応 | HTTPエラーをユーザー向け文言へ変換。ネット切断時は表示と再取得操作。不可逆な再送は状態照会後に判断 |
| 整合性 | 在庫と受注の更新はサーバーでトランザクション管理。クライアントだけの制約を信用しない |
| 認証 | TLS、短命アクセストークン、更新トークンの安全保管・失効、RBAC、秘密情報非ログ化 |
| 保守 | ビルド/静的解析、単体・API統合・UIスモークテスト、フォーマッタとnullable参照型 |
| 配布 | Windows向けMSIX（証明書や信頼設定は開発用手順を明記）。署名配布の本番運用は別課題 |
| 監査 | 重要な書込と取消・確定のユーザー、時刻、対象、理由を保管 |

## 9. issue-driven-kit適用要件

現行`issue-driven-kit`はUnity版とNode版が提供され、**汎用.NET版は未提供**。Unity版をWinUI 3にそのまま適用したと仮定しない。

1. `.NET版`の実行アダプター/editionを**キット本体側で新設し、別Issueで検証**してから、このサンプルへ導入する。
2. キットの共通仕様（`shared/spec/issue-run-spec.md`）を正とし、変更が必要なら先に仕様と共通fixtureを更新する。
3. `.NET`の検証コマンド（`dotnet test`、`dotnet build`、UIスモーク）を、キット仕様が要求する合格条件・終了コード・保護ファイル機構に安全に接続する。
4. 自動化できない対話UIの人手確認は、機械的な`PASS`と分けて記録する。WindowsでGUIテストを行う実行セッションを確保。
5. Issueごとに仕様、確認コマンド、依存関係、変更許容範囲、実行ログ/レビューを残す。秘密情報の公開は禁止。

## 10. 完了条件

NET-F-01～14を実装しNET-AC-01～15を検証。第三者がREADMEでAPI・Windowsクライアントを起動し、受注→請求→PDF出力を再現できる。CIでサーバー・共通ロジックのテストが合格し、GUI実機試験とMSIX導入試験を別途記録する。未検証項目はPASSと表示せず未検証として公開。

## 11. 制約・前提・未決

- Windows専用開発/テスト環境が必要。Linux上のGitHub ActionsだけではWinUI実行テストを保証できない。
- WinUI3のグリッド操作に採用する具体的コントロールはアクセシビリティとライセンスを確認して決定する。
- ローカル認証アカウント方式はサンプル用。実企業運用では企業IdP連携等を別途設計する。
- API配備先、証明書、署名証明書、帳票用PDFライブラリは初期ADRで確定する。
