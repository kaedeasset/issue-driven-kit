## 1. 背景と目的

GitHub Issueから生成AI（Claude Code）が設計・実装・テスト・修正を進める `issue-driven-kit` の有効性を、新規業務Webアプリの開発を通して公開・再現可能な形で示す。実務で現れる認証、権限、マスター、受注、在庫、請求、DB整合性、API、画面、テストを含める。

**評価対象はアプリの機能だけでなく開発プロセス**である。Issue、受入条件、テスト実行、変更履歴、結果を追跡できるようにする。既存システム移行・保守は対象外とする。

## 2. システム概要

- 仮称：SalesFlow TS。
- クライアント：ブラウザ（PCの最新安定版Chrome・Edgeを優先）、React + Next.js + TypeScript。
- サーバー：Node.js + NestJS + TypeScript、REST/JSON API。
- データベース：PostgreSQL。ORM：Prisma。
- クライアントとAPIは独立したアプリとして実装・テストできること。
- 対象利用者：管理者、営業担当、閲覧担当。日本語UI、通貨JPY、標準時刻はUTC保存・JST表示。
- 開発・試験の環境：Windows 11 の PC 1 台。PostgreSQL 17 を Windows のサービスとして入れておき、DB は `salesflow_ts_dev`・`salesflow_ts_test`（共通 §2）。Docker は使わない。

## 3. 対象範囲

### 3.1 MVPに含める機能

| ID | 機能 | 要件 |
|---|---|---|
| TS-F-01 | ログイン/ログアウト | ユーザー認証、セッション期限、認証失敗応答 |
| TS-F-02 | ロール管理 | `admin` / `operator` / `viewer` の3ロール。APIでも強制 |
| TS-F-03 | 顧客マスター | 登録、一覧、検索、詳細、編集、無効化。顧客コード一意 |
| TS-F-04 | 商品マスター | 登録、一覧、検索、詳細、編集、無効化。商品コード一意 |
| TS-F-05 | 在庫照会・調整 | 現在庫を表示。管理者が理由付きで調整できる |
| TS-F-06 | 受注下書き | 顧客と複数明細を保存・変更。数量・単価を検証 |
| TS-F-07 | 受注確定 | 在庫不足を防ぎ、在庫減算と状態遷移を一取引で実行 |
| TS-F-08 | 受注取消 | 請求前の確定受注のみ取消可。在庫を戻す |
| TS-F-09 | 請求書発行 | 確定受注に対し請求書を一度だけ発行。明細・金額を固定 |
| TS-F-10 | 履歴・監査 | 状態変更と在庫調整の操作者、日時、理由、対象IDを保存 |
| TS-F-11 | 検索・ページング | 顧客、商品、受注、請求書の絞り込み、ソート、ページング |
| TS-F-12 | テスト用データ | 固定データ投入とDB初期化方法。再実行して同じ結果 |
| TS-F-13 | 運用確認 | ヘルスチェック、構造化ログ、障害時の追跡ID |

### 3.2 MVP対象外

決済連携、実在顧客データ、複数会社・複数倉庫、配送、値引き、税率混在、会計連携、メール送信、PDF帳票の高度なレイアウト、スマートフォン最適化、オフライン編集、本番向け多要素認証。将来のIssue候補とし、MVP受入条件に混ぜない。

## 4. 主要業務ルール

| ID | ルール |
|---|---|
| TS-BR-01 | 金額はJPY整数（最小単位1円）で保持し、浮動小数点で金額を計算しない |
| TS-BR-02 | 明細金額＝単価×数量、税抜計＝明細金額の合計、消費税＝`floor(税抜計×0.10)`、税込計＝税抜計＋税。税率10%は**サンプル用固定仕様**であり税務一般の正解を示さない |
| TS-BR-03 | 数量は1以上9999以下、単価は0以上9,999,999以下、明細は1受注あたり1～100行 |
| TS-BR-04 | 状態：`DRAFT → CONFIRMED → INVOICED`、`DRAFT → CANCELED`、`CONFIRMED → CANCELED`。それ以外は禁止 |
| TS-BR-05 | 受注確定時に在庫を減らし、取消（請求前）で戻す。取消・確定の重複実行で在庫が二重計上されない |
| TS-BR-06 | 受注確定時点の品名と単価を明細にスナップショット保存し、マスター変更で過去の金額を変えない |
| TS-BR-07 | 請求書は受注に対し最大1件。発行後は内容変更不可。発行操作の再送は重複発行しない |
| TS-BR-08 | 同じ受注を同時更新した場合はバージョン競合として通知し、後勝ち上書きをしない |
| TS-BR-09 | 無効化した商品・顧客は新規受注で選択不可。既存記録は参照可能 |
| TS-BR-10 | ロール権限：viewer=閲覧のみ、operator=受注作成/確定/取消/請求、admin=全機能（在庫調整・ユーザー管理含む） |

## 6. 受入条件（機械判定できる仕様）

| ID | 入力・操作 | 期待結果 |
|---|---|---|
| TS-AC-01 | P001=単価1000・在庫10、P002=単価350・在庫3、数量2と1の受注 | 税抜2350、税235、税込2585 |
| TS-AC-02 | TS-AC-01を確定 | P001在庫8、P002在庫2、状態CONFIRMED |
| TS-AC-03 | P002数量4を確定 | 在庫不足エラー。受注状態・両商品の在庫は不変 |
| TS-AC-04 | 確定受注を取消 | 在庫が元に戻り、状態CANCELED。再取消でも増えない |
| TS-AC-05 | 確定受注を請求 | 請求書1件、税込2585、状態INVOICED。再実行でも件数1件 |
| TS-AC-06 | 請求済み受注を取消 | 409相当の業務競合、DB変更なし |
| TS-AC-07 | viewerが受注作成APIを実行 | 403。UIの非表示だけに依存しない |
| TS-AC-08 | 同一versionで同時に更新 | 一方のみ成功、他方は409。履歴整合性維持 |
| TS-AC-09 | マスター単価を変更後、既存請求を照会 | 請求金額は発行時と同一 |
| TS-AC-10 | 初期化・固定データ投入・全テストを2回連続実行 | 毎回同一の期待結果、終了コード0 |
| TS-AC-11 | ログアウト後に保護APIを要求 | 401。機密フィールドを返さない |
| TS-AC-12 | 誤った入力（数量0、重複コードなど） | 項目別エラー、DBに不正レコードが残らない |

## 7. 非機能要件

| 分類 | MVP要件・測定方法 |
|---|---|
| セキュリティ | パスワードは強固なハッシュで保存。サーバー側認証/認可。セッションCookieはHttpOnly/SameSite/Secure（HTTPS時）。CSRFを考慮。秘密情報をコミット・ログに出さない |
| 整合性 | 確定・取消・請求はDBトランザクション。外部キー・一意制約・楽観ロックを使用 |
| 性能 | ローカル開発環境の固定データ（顧客1千、商品1千、受注1万）で主要一覧API p95 500ms以内を**目標**（計測し未達は報告） |
| 可用性 | MVPは単一構成。復旧手順・DBマイグレーション・バックアップ手順を文書化。本番SLAは設定しない |
| 保守性 | TypeScript strict、lint、型チェック、単体・統合・E2Eテスト、OpenAPI定義 |
| 再現性 | Node/npm、依存関係lock、PostgreSQL 17（Windows のサービス。DB とユーザーを作る手順を README に書く）、シード、起動・試験コマンドを固定。試験は毎回 `salesflow_ts_test` を作り直す |
| アクセシビリティ | キーボード操作、フォームラベル、エラー表示、基本的なコントラストを確認 |
| 運用 | JSONログ、correlation ID、ヘルスチェック。実際の個人情報は投入禁止 |

## 8. issue-driven-kit適用要件

1. キットの **Node 版**を入れる。`--dry-run` → 入れる → 点検（doctor）の順で確かめ、入れたキットの版を `.issue-kit/version` に残す（共通 §3）。
2. 課題は GitHub Issue を正とし、各 Issue に目的・変更範囲・`## 前提`・`## 合格の条件`（```` ```js ```` の確認コマンドと条件の行）を書く。
3. **昼に人が Issue を書き、夜に無人の回が連続して実装する**（共通 §1.3）。その夜に回す Issue は前の日の昼に書く。新しい API と画面は、実装の 1 晩前の夜に詳細設計を書かせ、人が昼に読んで直す（共通 §3.2）。1 件は本体とテストで 400〜700 行（共通 §4.1）。詳細設計の単位は基本設計 11.2、Issue の並びは 案件のリポジトリの `docs/guides/working/issue-plan.md`（Claude Code が作る。共通 §4.4）。
4. 無人の回の合格だけでは人の受け入れにしない。`claude-done` の後に人が差分を読んで閉じる。落ちた Issue は、直したら人が閉じる（共通 §4.2）。
5. テストの入口は `node scripts/test.mjs`（`Result:` 行・PASS 0・FAIL 1・0 件は FAIL）。vitest は `issueKit.testRunner` で回す。型チェック・lint・Playwright を同じ入口で回すのは、キットの準備 P-1 の後（共通 §3）。P-1 の前は、T01 で vitest の中から型チェックを呼ぶ形にする。
6. 「PASS が出た」だけでなく、TS-AC 群の期待値をテストで確かめる。0 件のテストが FAIL、わざと落とすと非 0 になることを T01 で確かめる。
7. 計測は共通 §5 のとおり（無人の回のまとめ・費用の換算・行数・テストの件数・`docs/inspecs/<年>/<月>/worklog.md` の人の時間）。
8. Issue 本文・コミット・テストの結果・失敗とやり直しの記録を公開できる形で残す。秘密の値・PC の中のパス・モデルとの非公開の会話は公開しない。

## 9. リリース判定

- TS-F-01～13 実装、TS-AC-01～12 自動テスト合格（`node scripts/test.mjs` の `Result: PASS`）。
- 初期化からアプリ起動、ログイン、受注→請求まで、第三者が README どおりに再現できる（PostgreSQL を入れるところから）。
- 重大な認証回避・二重請求・在庫不整合が 0 件。
- CI（GitHub Actions・`services: postgres` は `postgres:17`）で型チェック、lint、単体・統合テストが成功し、E2E の結果が記録されている。CI の合否は公開する回（回5）で判定する（計画 E7）。
- 全 Issue の合否・人のレビューの結果を確認できる。

## 10. リスク・未決事項

- Next.js の認証処理と NestJS の認証境界：基本設計で BFF 方針を定義済み。
- クライアント・API 間の Cookie/CSRF/CORS：ローカルと公開構成で異なるため、環境ごとに設定を固定する。
- 型チェック・lint・Playwright をテストの入口にまとめる形は、キットの準備 P-1 で決まる。P-1 が遅れたら T01 の形（vitest から型チェックを呼ぶ）で進める。
- 使う物の版は基本設計 1.1 でメジャーとマイナーまで決める。パッチは初回の環境構築（C1）で lock に固定する。
- 1 件 25〜50 分という時間は見積もり。回1の夜1の実測で、夜ごとの件数を直す。
